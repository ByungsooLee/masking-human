# 開発時の必読・変更手順

更新日：2026-10-23。[English](en/development-workflow.md)

## 実装前に読む

開発・修正・リファクタリング・プロンプト調整の前に、ルートの [AGENTS.md](../../AGENTS.md)、[索引](README.md)、[現行仕様](current-spec.md)、[判断記録と未決事項](decisions-and-open-questions.md) を読みます。会話・プロンプト・分析を触る場合は [実践集](interview-playbook.md) と [評価](quality-evaluation.md) も読み、該当する [出典](sources/README.md)・実装・既存テストを確認します。英語の対応文書でも構いません。

着手時に読んだファイルと維持すべきルールを簡潔に示します。資料を読んだだけでコードの現状を推測せず、編集対象と呼び出し元を確認します。Next.jsのコードを書く前には、AGENTS.mdに従ってインストール済みバージョンのガイドも読みます。

## 意図しない上書きを避ける

1. `git status` と既存差分を確認し、ユーザーや他の作業の変更を戻したり上書きしたりしません。
2. 今回の依頼の範囲、維持する挙動、変更する挙動、関連する判断IDを整理します。リファクタリング・翻訳・デザイン修正から無関係な仕様変更へ広げません。
3. 現行実装／現行指示／提出資料の知見／提案・未決の区分を維持します。原資料や旧仕様の例を、そのまま実行プロンプトや新仕様へ転記しません。
4. 資料とコード、または日英が食い違う場合は差異を明示します。既存判断とユーザーの指示から解決できる部分は進め、意図の判断が必要な部分だけ確認します。コードを正当化するために資料を黙って書き換えません。
5. 許可済みの仕様変更では、理由・変更前後・影響・根拠・検証を判断記録に追記し、対象仕様と関連テストを同じPRで更新します。以前の記録を消さず、変更先を示して履歴を残します。既存のユーザー許可を取り直す必要はありません。

通常の実装は、明記された現行仕様を基準とします。モデルの出力保証や未実装機能を、資料を整えるだけで実現した扱いにしません。

## 日英と原資料の管理

- 日本語のルート文書が編集元、`en/` が対応訳です。英訳は別仕様を定義しません。日本語と英語の意味が一致するよう、同じPRで更新します。
- 見出しや言い回しは自然に訳し、数値・制約・根拠ID・判断ID・未決の状態をそろえます。内容上の不一致は単純な日本語優先で隠さず、コードと判断記録を確認して解消します。直接のユーザー指示が優先します。
- 各文書に対応言語へのリンクを付けます。索引・出典・変更履歴にも更新を反映します。
- `sources/2026-10-23-notebooklm-export.md` は受領原文の保存コピーです。修正・翻訳で上書きせず、追加資料は新しい日付付きファイルに保存します。翻訳や要約を追加する場合も原資料と区別します。
- 原文にない出典・本人の感情・因果・家族関係・同意条件を補いません。最新の原資料でも自動的に採用済みとはしません。

## レビューと完了条件

PRのテンプレートに、読んだ資料、仕様上の影響、日英更新、判断記録、確認結果を記載します。文書のみ・挙動変更なしならその旨と理由を明記し、無関係な文書の更新は不要です。

関連するリンクと差分を確認し、変更に適したテストとCIを通します。プロンプトや会話ロジックを変える場合は評価観点との対応を確認し、モック成功と実音声品質を区別します。有料API・実メールの実行は既存の許可範囲に従います。

この手順とPRテンプレートは開発・レビューのルールです。全開発者の読了、英訳の意味的一致、仕様順守を自動的に保証する仕組みではありません。
